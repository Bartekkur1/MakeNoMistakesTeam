## Pattern Assignments

### Route handlers (`src/app/api/**/route.ts`)

**Source:** `web-app/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md`

Supported exported methods (lines 24-40): `GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS`. If `OPTIONS` is not exported Next auto-implements it with only an `Allow` header - **no CORS headers**, so we must export `OPTIONS` explicitly in every route file.

**Next 16 change - `params` is a Promise** (lines 85-90):
```ts
export async function GET(
  request: Request,
  { params }: { params: Promise<{ team: string }> }
) {
  const { team } = await params
}
```

**Preferred typed form - `RouteContext` global helper** (lines 107-121; types generated by `next dev`/`next build`/`next typegen`, no import needed):
```ts
import type { NextRequest } from 'next/server'

export async function GET(_req: NextRequest, ctx: RouteContext<'/users/[id]'>) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```
Apply as `ctx: RouteContext<'/api/cases/[id]'>` and `RouteContext<'/api/cases/[id]/replies'>`. Note: a fresh `tsc` before typegen will not know `RouteContext`; plan verification via `npm run build` (which generates types) or use the explicit `{ params: Promise<{ id: string }> }` form.

Query string (lines 66-71): `request.nextUrl.searchParams.get("demo_child_id")` with `NextRequest`.

**CORS** (lines 525-540):
```ts
return new Response('Hello, Next.js!', {
  status: 200,
  headers: {
    'Access-Control-Allow-Origin': '*',
    'Access-Control-Allow-Methods': 'GET, POST, PUT, DELETE, OPTIONS',
    'Access-Control-Allow-Headers': 'Content-Type, Authorization',
  },
})
```
Recommended: centralize in `src/lib/http.ts` so every response (including errors) carries CORS headers; `*` origin is fine (no cookies/auth) and covers `chrome-extension://` and the mobile page. Include `PATCH` in Allow-Methods. Alternative: global `headers()` in `next.config.ts` (docs `05-config/01-next-config-js/headers.md`) for `/api/:path*`, but OPTIONS handlers are still needed for 204 preflight. `proxy.ts` (Next 16 rename of middleware, `03-file-conventions/proxy.md`) is an option but adds complexity - not needed.

Suggested skeleton (to be established by this phase):
```ts
// src/app/api/cases/[id]/route.ts
import type { NextRequest } from "next/server";
import { json, apiError, preflight } from "@/lib/http";
import { getCase } from "@/lib/cases/repository";

export const dynamic = "force-dynamic"; // never cache live DB reads

export function OPTIONS() { return preflight(); }

export async function GET(_req: NextRequest, ctx: RouteContext<"/api/cases/[id]">) {
  const { id } = await ctx.params;
  try {
    const c = await getCase(id);
    if (!c) return apiError(404, "case_not_found", "Sprawa nie istnieje");
    return json(c);
  } catch {
    return apiError(503, "storage_unavailable", "Baza niedostępna");
  }
}
```
Body parsing: wrap `await request.json()` in try/catch -> 400 `invalid_json`. Never return 2xx unless the Supabase insert returned the row (widget ERR-01: no false save confirmation).

## Shared Patterns

- **Error format** (all routes): one helper `apiError(status, code, message)` -> `{ "error": { "code", "message" } }` + CORS headers. Codes: 400 validation/invalid_json, 404 not found (also for malformed UUID), 503 DB unavailable/config missing, 500 unexpected.
- **CORS** (all routes): from `src/lib/http.ts`, every response + exported `OPTIONS` returning 204.
- **Caching**: `export const dynamic = "force-dynamic"` on GET route files so lists reflect writes.
- **Secrets**: Supabase client imported only from `src/lib/**` server modules, never from client components.
