## Kontrakt i zależności

MSG_GUARDIAN_REQUEST = aura/guardian-request. requestGuardianVerification(case, result) wysyła { type, case, result }; result to kopia aktualnego wyniku z summaryKey, signals, unknowns, step i mismatches, bez tłumaczenia kluczy na treści i bez odczytu draft/pendingSelection. Zachować MSG_CASE_APPROVED, submitCase i self.__aura.cases. SW zapisuje wyłącznie poprawną prośbę w guardianRequests (limit 100 jak cases), odpowiada { ok: true }; niepoprawny payload od uprawnionego nadawcy daje { ok: false } bez rekordu. Istniejące sprawdzanie sender.id i sender.tab obowiązuje również nowy typ. Walidować isValidCase oraz strukturę wyniku i klucze względem istniejącego kontraktu check.js/STRINGS, bez mutacji danych i bez nowego publicznego kontraktu backendu. Log messages zachowuje dotychczasową semantykę: jeden wpis na wiadomość, nowy typ dodaje jeden wpis tylko przy jawnym kliknięciu.

Store udostępnia beginGuardianRequest(), guardianRequested(token), guardianRequestFailed(token). Początek wymaga view=result, gotowego check.result, braku draft oraz braku aktywnej transakcji; zwraca token lub null i ustawia oczekiwanie bez usuwania wyniku. Można współdzielić submitting/gen z zatwierdzeniem, ale submitFailed nadal obsługuje wyłącznie podgląd; błąd prośby musi wracać do result. W trakcie oczekiwania zablokować prośbę, poprawianie odpowiedzi, edycję i nowe zaznaczenie także w store. Close/hide nadal działają. Sukces z aktualnym tokenem ustawia check.step i resumeStep na confirmation oraz widok confirmation, chyba że okno zamknięto; wtedy pozostaje closed do wznowienia. checkView musi jawnie rozpoznawać confirmation. Błąd zachowuje case/answers/result, usuwa oczekiwanie i używa osobnego klucza guardianRequest; reset dokumentu unieważnia token. Confirmation ma Zamknij z fokusem; ponowne otwarcie nie wysyła ponownie. D-09 zachowuje pamięć karty, D-11/D-12 wymagają nowego sprawdzania po zatwierdzeniu zmienionej treści.

Task 1 potrzebuje 02-03 i tworzy cały osiągalny przepływ; task 2 rozszerza jego walidację i obsługę przerwań; task 3 dokumentuje demo i sprawdza regresje. Wszystkie has_checkpoint=false. Wave 4 wynika z zależności oraz wspólnych plików z wave 3. Jeden plan jest wymagany przez orkiestratora: wyjątek od limitu pięciu plików tracera obejmuje siedem małych plików istniejącego przepływu i dwa pliki testowe. Rozdzielenie warstw pozostawiłoby nieosiągalną akcję; zakres jest jedną luką, bez drugiego podsystemu. Estimate jest projekcją zakresu, confidence low; w tej sesji nie uruchamiano kalibracji ani implementacji.
